# Shared consumer-pipeline vectors

Documents that **every** runtime's §7.2 pipeline runs: `trust-tasks-rs` (`tests/received_digest.rs`), `@openvtc/trust-tasks` (`test/envelope.test.ts`), `trust-tasks-go` (`trusttasks/item11_vectors_test.go`) and `trust_tasks` (`test/input_robustness_test.dart`). A change that makes one runtime disagree fails that runtime's CI.

`item11-digest.json` pins [SPEC §7.2](../../SPEC.md) item 11's *Keying and comparison*: two documents under one `id` are the same document only when their serializations are identical under RFC 8785 canonicalization. Each case consumes `first`, then `second`, against one replay guard, with a payload type that models only `payload.subject`, and passes each document to the pipeline as received. `expect` is the second outcome: `duplicate` (absorbed, the handler does not run again), or the code it is refused with — `idConflict` or `expired`. The cases that differ only in a member the payload type drops, or in the spelling of a timestamp, are the ones a digest over the typed reading gets wrong. A case may carry its own `first`; otherwise the top-level one is used. The number cases pin RFC 8785's reading of every number as an IEEE 754 double: `1` and `1.0`, or `100` and `1e2`, are one number and so one document. The cases with `secondAt` pin *Bounding the record*: such a case consumes its `second` at that instant, under the consequential checks' five-minute maximum age, 30-day expiry horizon and sixty seconds of skew. In the first pair the acceptance window is half-open and ends where the record's retention does, so a resend one millisecond before `issuedAt + 6 min` is a `duplicate`, and one at exactly that instant is refused `expired` — never accepted after its record may have been dropped. The second pair pins the same boundary for an `expiresAt` beyond the expiry horizon, which is clamped there: the window ends at `issuedAt + 30 days + 60 s`, and is half-open in the same way.

One known difference remains in the canonical forms and is not a vector: Rust and Go order object members by Unicode scalar value, TypeScript and Dart by UTF-16 code unit, as JCS does. They disagree only for member names mixing characters above the BMP with names in `U+E000..U+FFFF`, and since each runtime orders both documents it compares the same way, the equality it induces — which is all item 11 uses — is unaffected.

`timestamps.json` pins how `issuedAt` and `expiresAt` are read (SPEC §4.2, RFC 3339 `date-time`): each runtime's reader must accept every `valid` value as the instant `epochMs`, and refuse every `invalid` one. Out of range means a month outside 1-12, a day the month does not have, hour 24, minute or second 60 (no leap second), or an offset beyond 23:59. Each language's own date parser accepts, refuses or rolls over a different subset of these. `Date.parse` reads `2026-02-30` as 2 March, `DateTime.tryParse` reads `2026-13-45T25:61:61Z` as February 2027, chrono reads `:60` as a leap second, and Go's `time.Parse` accepts `+24:00`. So every runtime checks the ranges itself. Run by `trust-tasks-rs/tests/timestamps.rs`, `trust-tasks-ts/test/timestamps.test.ts`, `trust-tasks-go/trusttasks/timestamps_internal_test.go` and `trust-tasks-dart/test/timestamps_test.dart`.

`freshness.json` pins the acceptance window of SPEC §7.2 (items 4 and 13, *Bounding the record*). Each case runs item 4's expiry check and then the freshness bound at `now`, under a named policy, and for an accepted document also the instant its replay record may be dropped. A stated `expiresAt` replaces the maximum age over `issuedAt`, up to an expiry horizon after `issuedAt`; an `expiresAt` beyond the horizon is clamped to `issuedAt + horizon + skew`, for acceptance and for the record alike, and the horizon does not apply to a document without an `issuedAt`. Every window is half-open: a document is accepted one millisecond before its edge and refused at it. The `default` and `consequential` policies must equal each runtime's own (sixty seconds of skew; and five minutes, thirty days and `issuedAt` REQUIRED for the consequential one). Run by `trust-tasks-rs/tests/freshness_vectors.rs`, `trust-tasks-ts/test/freshness-vectors.test.ts`, `trust-tasks-go/trusttasks/freshness_vectors_test.go` and `trust-tasks-dart/test/freshness_vectors_test.dart`.

The documents are stored as JSON text, not objects, so member order and whitespace reach each runtime exactly as written.

`ext-critical.json` pins [SPEC §4.5.2](../../SPEC.md) (*Marking a Namespace Critical*): each case checks a payload against `ext-critical.schema.json` with a set of namespaces the consumer recognizes. A namespace named in `extCritical` and not recognized is `unsupportedExtension`; an `extCritical` that is not a non-empty array of unique reverse-DNS names, each an immediate key of the sibling `ext`, is `malformedRequest`. A marking is read only at an object level whose schema declares an `extCritical` property (through `$ref` and every `allOf` / `anyOf` / `oneOf` branch); at a level the schema closes without declaring it the member is `malformedRequest`, and in an open object, or inside an `ext` namespace's content, a member of that name is data. With no schema, every level outside `ext` content is read. Run by `trust-tasks-rs/tests/ext_critical.rs`, `trust-tasks-ts/test/ext-critical.test.ts`, `trust-tasks-go/trusttasks/ext_critical_test.go` and `trust-tasks-dart/test/ext_critical_test.dart`.
