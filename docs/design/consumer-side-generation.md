# Consumer-side generation — compile only what you use

Status: **proposed** (2026-10-26); milestone 1 **implemented** — see
[Milestone 1 — implemented](#milestone-1--implemented). Supersedes generating
every specification into every library.

## The problem

Every library generates every specification version in the registry —
1,126 versions of 738 tasks today — and every consumer compiles all of it.
Measured on main, 2026-10-26:

| | Package | Generated source | Consumer build | Peak memory |
|---|---|---|---|---|
| Rust `trust-tasks-rs` | 9.96 MB `.crate` (crates.io limit: 10 MB) | 87 MB | 166 s | 16 GB |
| TypeScript `@openvtc/trust-tasks` | 8.1 MB tarball, 109 MB unpacked | 25 MB | 5 s | 1.3 GB |
| Go `trust-tasks-go` | module | 25 MB | 7 s | 0.3 GB |
| Dart `trust_tasks` | 3 MB | 30 MB | 2 s | 0.4 GB |

A consumer using three tasks pays for 1,126. Growth is linear in the registry:
at 5,000 tasks the Rust crate would be ~60 MB, and a build ~100 GB of memory.
Optimising each generated module (prototyped: compact schemas, no doc-schema
blocks, plain strings for constrained strings, deduplicated shared types) buys
2–3×, which moves the wall rather than removing it — a single package per
language stops being publishable somewhere around 1,500–2,000 tasks however lean
each module is.

## The model

**The libraries ship the runtime. An application generates the tasks it uses.**

```
registry (trusttasks.org)            application repository
─────────────────────────            ──────────────────────────────────────────
/spec/<slug>/<M.N>/bundle.json  ──►  trust-tasks add vault/upsert/0.4
   schema + policy, by digest          ├─ trust-tasks/vault/upsert/0.4.bundle.json  (vendored)
/spec/index.json                       └─ trust-tasks.lock  (slug, version, sha256)
   every version, digest, status
                                     build:
                                       Rust  build.rs → trust-tasks-build → OUT_DIR
                                       Go    go generate
                                       Dart  build_runner
                                       TS    trust-tasks generate --lang ts
```

### The bundle

One JSON document per specification version, everything a generator needs and
nothing it does not:

```json
{
  "typeUri": "https://trusttasks.org/spec/vault/upsert/0.4",
  "slug": "vault/upsert", "version": "0.4",
  "status": "draft", "deprecation": null, "extends": null,
  "policy": { "proof": {"request": true, "response": true}, "issuedAt": {…},
              "recipient": {…}, "bearer": false, "maxDocumentBytes": {…} },
  "errorCodes": [ … ],
  "schema": { …self-contained, $refs inlined… },
  "responseSchema": { … }
}
```

Addressed by the SHA-256 of its canonical (JCS) bytes. `index.json` lists every
version with its digest and lifecycle status, so `update` can find a successor
and refuse a withdrawn version.

### The lockfile

`trust-tasks.lock` (TOML) names each pinned version and its digest; the bundles
sit beside it, vendored. Builds read only the vendored files — **no network at
build time**, reproducible, and a code review sees exactly which task versions
moved. `trust-tasks check` verifies every bundle against its digest (CI).

### The CLI — `trust-tasks` (Rust binary)

`add <slug>[/<M.N>]`, `remove`, `update [--to-latest]`, `check`, `list`,
`generate --lang <rs|ts|go|dart> --out <dir>`. Distributed as a static binary
and via `cargo install`. Generation reuses the generators: the Rust codegen as a
library; the TS/Go/Dart generators ported behind the same bundle input (see
milestones — until ported, `generate` invokes them through Node).

### What stays bundled in each runtime

The framework's own specifications — `trust-task-error`, `trust-task-discovery`,
`trust-task-next-step`, `trust-task-ok`, `trust-ceremony-receipt` — because the
runtime itself speaks them. Everything else is generated by the application.

### What stays the same in this repository

CI still runs all four generators over **every** specification, and
`check-bindings` still holds them to agreement with each other and with the
front matter. Only what is *published* changes. The hand-written packages
(HTTPS, DIDComm, TSP, proof, capability client) generate the few specifications
they use at their own build time.

### What it buys

- Package size and build cost independent of the registry: an application with
  three tasks compiles three tasks, at 738 tasks or at 5,000.
- The quarterly withdrawal is no longer a breaking release of the libraries — it
  only constrains what `update` offers; a pinned bundle keeps building.
- `extends` pays off directly: `update` can move a pin along a declared
  extension with no code change.
- The per-module optimisations (compact schemas, plain strings, shared-type
  dedup) become per-task costs, worth doing but no longer existential.

## Migration — parallel, then remove

1. Ship the bundles, the lockfile, the CLI and per-language generation **alongside**
   the prebuilt modules.
2. Mark the prebuilt spec modules deprecated, pointing at `trust-tasks add`.
3. Remove them one quarter later, in one declared break per library, aligned with a
   withdrawal batch.

## Milestones

1. **Registry bundles + index** — `npm run build` emits `bundle.json` per version
   and `index.json`; the site serves them; digests stable across builds.
2. **Rust end to end** — `trust-tasks-build` (the codegen as a library, input:
   bundles), the `trust-tasks` CLI (`add`/`update`/`check`/`generate --lang rs`),
   and an example application using three tasks. Measure its build.
3. **TypeScript, Go, Dart generation from bundles** — each generator takes
   bundles as input; `generate --lang` drives it.
4. **Hand-written packages** move to build-time generation of what they use.
5. **Deprecate, then remove** the prebuilt modules (with a withdrawal batch).

Each milestone is releasable on its own; nothing is removed before milestone 5.

## Milestone 1 — implemented

`cargo run -p trust-tasks-codegen -- --bundles <out-dir>` (`npm run
build-bundles` writes into `website/specs/`) writes
`<out-dir>/<slug>/<M.N>/bundle.json` for every specification version and
`<out-dir>/index.json`, touching nothing in `trust-tasks-rs` (about 1.3 s for
the registry). `deploy.yml` runs it after `npm run build`, so the site serves:

- `https://trusttasks.org/specs/<slug>/<M.N>/bundle.json`
- `https://trusttasks.org/specs/index.json`

`/specs/` is the raw asset tree (an `ASSET_PREFIXES` entry in
`infra/cloudfront/type-uri-negotiation.js`), not the `/spec/` Type URI tree, so
no routing change was needed. Earlier drafts above say `/spec/…/bundle.json`;
it is `/specs/`.

**Built by the Rust codegen, from its own code paths.** The schemas come from
`spec_schemas()` — the inlining and response-document wrapping `generate_one`
uses for `PAYLOAD_SCHEMA` — and the policy from `read_spec_policy()`, the
front-matter readers `generate_one` uses for the policy constants. A bundle is
therefore, by construction, what the generator generates from.

**Bundle** (`bundleVersion: 1`, every member always present):

| Member | |
|---|---|
| `bundleVersion` | `1` |
| `typeUri`, `slug`, `version` | the request Type URI and its parts |
| `status` | front matter: `draft`, `candidate`, `standard`, `retired`, `withdrawn` |
| `deprecation` | the lifecycle note every library carries (`superseded by …`, `retired; use …`, `retired`), or `null` |
| `extends` | front matter `extends` (`"M.K"`), or `null` |
| `supersededBy`, `targetFrameworkVersion` | front matter, or `null` |
| `policy.bearer` | `IS_BEARER` |
| `policy.proofRequired.{request,response}` | `IS_PROOF_REQUIRED` per variant |
| `policy.issuedAtRequired.{request,response}` | `IS_ISSUED_AT_REQUIRED` per variant |
| `policy.recipientRequired.{request,response}` | `IS_RECIPIENT_REQUIRED` per variant — the response's tracks the *issuer* party (§7.2 item 5) |
| `policy.maxDocumentBytes.{request,response}` | `MAX_DOCUMENT_BYTES`, integer or `null` |
| `errorCodes[]` | `{code, meaning, retryable, detailsSchema?}`, declaration order, `detailsSchema` `$ref`s inlined |
| `propertyOrder` | (milestone 2) JSON Pointer of every schema object in `schema` / `responseSchema` that has `properties` → its member names in **authored** order, read from the file the definition was written in (the payload schema, or the shared file a `$defs` entry was spliced from). A reader of an older bundle treats it as `{}` |
| `defsOrder` | (milestone 3) `/schema` and `/responseSchema` → the root `$defs` names in the order the TypeScript, Go and Dart generators declare them: the payload schema's own as authored, then each spliced definition in the order their inliners' last-in-first-out `$ref` frontier reaches it. A reader of an older bundle treats it as `{}` |
| `defOrigins` | (milestone 3) each `$defs` entry spliced in from another document → `<that document's $id>#/$defs/<name>` (a document with no `$id`: its path under the specifications root, below the Type URI prefix). One shared component carries the same origin in every bundle, so a generator can declare it once; the payload schema's own definitions have none. A reader of an older bundle treats it as `{}` |
| `schema` | the request payload schema, self-contained — `Payload::PAYLOAD_SCHEMA` |
| `responseSchema` | the response document — `Response::PAYLOAD_SCHEMA` — or `null` when there is no `$defs.Response` (then the `response` policy values carry no meaning) |

The policy is per variant rather than the single `recipient` the sketch above
had, because the generated libraries already hold it per variant.

**Canonical form and digest.** Compact, members sorted by UTF-16 code unit,
JCS string escaping, integers only (a float that has no unambiguous JCS form
stops the build) — i.e. RFC 8785. The digest is `sha256:<hex>` of exactly the
bytes of `bundle.json`, no trailing newline. Two runs give identical bytes.

**Index** (`indexVersion: 1`, same canonical form): `generatedFrom` (the git
commit, or `null`), `bundleVersion`, `excluded` (slugs with no bundle and why),
and `specs[]` of `{typeUri, slug, version, status, deprecation, extends, digest,
path}` sorted by slug, then numerically by version; `path` is relative to the
index.

**What is bundled.** Every version, *withdrawn ones included* (`status:
"withdrawn"`), so a pinned bundle stays fetchable and verifiable after its
version leaves the libraries. `trust-task-error` is not: the runtimes model it
by hand (the codegen's `SKIP_SLUGS`), and `index.json` lists it in `excluded`.

**Checks.** Codegen unit tests compare five real bundles (deprecated, no
`$defs.Response`, `maxDocumentBytes`, `errorCodes` with `detailsSchema`) against
the module `generate_one` emits — schemas as parsed JSON, every policy constant,
`DEPRECATION`, `EXTENDS` — and run the whole registry twice for byte-identical
output, index-vs-disk agreement and digests. `scripts/check-bundles.mjs`
(`npm run check-bundles`, run in `deploy.yml` after the bundles are built)
checks independently: digests, canonical form re-derived with
`JSON.stringify`, the index against the tree, and every non-withdrawn bundle's
schemas against the **TypeScript** generator's `PAYLOAD_SCHEMA` /
`RESPONSE_PAYLOAD_SCHEMA`, every `defsOrder` against the order of those
schemas' `$defs`, and every `defOrigins` entry against the `$id`s and `$defs`
of the shared schemas in `specs/`.

Measured on main, 2026-10-26: 1,121 bundles, 14.6 MB in total, 13.0 KB
average, 56.8 KB largest; `index.json` 350 KB.

## Open before `bundleVersion` 1 is relied on (from building milestone 1)

1. **Member order.** The bundle's schema is key-sorted (it is the Rust codegen's
   inlined schema, which passes through a sorted map). The TS, Go and Dart
   generators read the authored order from `payload.schema.json`, so generating
   them from bundles (milestone 3) would reorder every struct's fields —
   harmless on the wire (proofs are over JCS) but churn in every generated file.
   Decision for milestone 2: the bundle carries the authored order, and the
   digest is defined over the JCS form of the bundle rather than the file bytes,
   so content identity stays independent of formatting. **Done in milestone 2**
   as `propertyOrder` (above). The digest stays `sha256` of the file bytes —
   which *are* the JCS form, so the two definitions coincide and a reader can
   verify without canonicalizing.
2. **Immutability.** A `draft` may be edited in place, so the bytes at
   `/specs/<slug>/<M.N>/bundle.json` can change while a lockfile pins the old
   digest. Milestone 2 adds an append-only store, `/specs/by-digest/sha256-<hex>.json`,
   never deleted by deploy, and `trust-tasks add`/`check` fetch by digest.
3. **Index size.** ~310 bytes an entry is ~1.5 MB at 5,000 tasks; split it per
   slug (`/specs/<slug>/index.json`) when the CLI needs it.
4. **Resolved fields.** `supersededBy` is raw front matter (may name a bare slug);
   resolve it to `slug/M.N` as `deprecation` already is, or drop it.

## Milestone 2 — Rust build side implemented

**`trust-tasks-build`** (new crate, `publish = true`) is the per-module Rust
generator as a library. An application's `build.rs`:

```rust
trust_tasks_build::Config::new()   // ./trust-tasks.lock + ./trust-tasks/
    .lockfile("trust-tasks.lock")
    .compile()?;                   // $OUT_DIR/trust_tasks_generated.rs
```

and `mod tasks { include!(concat!(env!("OUT_DIR"), "/trust_tasks_generated.rs")); }`
gives `tasks::vault::get::v0_3::{Payload, Response, error_codes, …}` — the module
path `trust_tasks_rs::specs` uses. Every vendored bundle is checked against the
lock's digest (and its slug/version/Type URI) before anything is generated;
`cargo:rerun-if-changed` names the lock and every bundle. Framework specs
(`trust-task-*`, `trust-ceremony-*`) are refused: the runtime carries them.
`Config::generate()` returns the source without writing — what
`trust-tasks generate --lang rs` calls.

**One generator.** `trust-tasks-codegen` now generates every `trust-tasks-rs`
module *through the bundle*: `build_bundle` → `Bundle::from_slice` →
`trust_tasks_build::generate_module(…, Target::runtime_crate())`. The committed
tree did not change by a byte, so each committed module is exactly what an
application generates from that version's published bundle, apart from the
paths below. The schema passes, typify settings, `render_module` and the
`errorCodes` reader moved into `trust-tasks-build` (with their tests).

**Paths.** A `Target` names the runtime: `crate` in the repository, `::trust_tasks_rs`
in an application. serde, serde_json, regress and chrono — what typify's output
names — are reached through `trust_tasks_rs::__private` (a `#[doc(hidden)]`
re-export module), every serde derive gets `#[serde(crate = "…")]`, and
`DeclaredErrorCode` (`#[non_exhaustive]`) is built through a hidden
`const fn __from_declaration`. An application depends on `trust-tasks-rs`
(`default-features = false`) and, as a build dependency, `trust-tasks-build` —
nothing else.

**Forward-minor routing.** `extension::extends_for` consults the runtime's
generated table, then declarations an application registered with the new
`extension::declare_extends(&'static [(&str, &str)])`. The generated file ends
with `EXTENDS` (every locked version's `extends`) and `declare_extends()`,
which an application calls once at start-up. Additive: no existing signature
changed.

**Example.** `examples/consumer-app` pins `acl/grant/0.2`, `keys/list/0.2` and
`vault/get/0.3`, builds with `trust-tasks-rs` `default-features = false`, and
runs a round trip through a `Dispatcher` (a response, a declared error code, a
policy refusal, and an unlocked type refused). `rust.yml`'s `consumer-app` job
builds and runs it.

**Measured** (Apple M5 Max, 18 cores, 64 GB; cold target directory, sccache
off, `RUSTC_WRAPPER= CARGO_TARGET_DIR=<fresh> /usr/bin/time -l cargo build …`):

| Build | Wall | Peak RSS |
|---|---|---|
| `-p trust-tasks-example-consumer-app` (3 tasks generated at build time, incl. building typify/syn for the build script) | **8.1 s** | **0.41 GB** |
| `-p trust-tasks-rs` (default features: every prebuilt module) | 140.2 s | 17.4 GB |
| `-p trust-tasks-rs --no-default-features --features acl,keys,vault` (today's family gating) | 13.9 s | 1.8 GB |
| `-p trust-tasks-rs --no-default-features` (the runtime alone) | 5.8 s | 0.41 GB |

The generated file for the three tasks was 418 KB (8,286 lines) when measured,
and is 335 KB (6,800 lines) since the generator took #926's compact schemas and
dropped the rustdoc schema blocks; after a lock change, regenerating and
recompiling the application takes 1.1 s.

## Milestone 2 — the CLI

### Using the CLI

`trust-tasks` is the `trust-tasks-cli` crate (`cargo install trust-tasks-cli`;
reference in [its README](../../trust-tasks-cli/README.md)). In an application:

```sh
trust-tasks add vault/upsert acl/grant@latest   # writes trust-tasks.toml, trust-tasks.lock, trust-tasks/
git add trust-tasks.toml trust-tasks.lock trust-tasks/
trust-tasks check                               # in CI: offline, exits 1 on any problem
trust-tasks update                              # later: move `latest` pins, report newer versions
```

- `add <slug>` pins the latest live version exactly, `<slug>/<M.N>` that
  version, `<slug>@latest` records the intent to follow the latest live version
  (neither `retired` nor `withdrawn`). A withdrawn version is refused.
- `update` moves a `latest` pin and says what the move costs: `0.5 extends 0.4:
  no code change needed` when the newer version's `extends` chain reaches the
  pinned one, `breaking: …` otherwise. An exact pin stays put (`--to-latest`
  moves it) but takes new bytes if its draft changed in place. A pin whose
  version has since been withdrawn is refused, left building, and fails the run.
- `check` is offline: each lock entry's vendored bundle exists and hashes to the
  locked digest, no stray bundles, manifest and lock agree.
- `fetch` restores missing or altered vendored bundles **by the locked digest**,
  never moving a pin — which is what the by-digest store is for: after a draft
  changes in place, its old digest is still fetchable.
- `list [--remote]` shows status, deprecation and, remotely, the newest version.
- `--registry <url>` / `TRUST_TASKS_REGISTRY` select another registry: an
  `https://` site root, a `file://` URL or a directory with the same layout.

The formats are as specified for milestone 2: `trust-tasks.toml` (intent;
additionally, a value may be an array of exact versions to pin two versions of
one task), `trust-tasks.lock` (`version = 1`, `registry`, `[[task]]` of `slug`,
`version`, `type_uri`, `digest`, sorted by slug then numerically by version),
and the digest is `sha256` over the bundle file's bytes.

### The by-digest store

`deploy.yml` runs `scripts/write-by-digest-store.sh website/specs` after the
bundles are built and checked, copying each bundle to
`specs/by-digest/sha256-<hex>.json` and re-hashing it. The deploy job uploads
that prefix **first and without `--delete`** (`--size-only`, immutable cache
headers), then syncs the rest of the site with `--delete --exclude
"specs/by-digest/*"`, so a published digest is never removed by a later deploy.
Until the store has every digest a lockfile can name, the CLI falls back to
`specs/<slug>/<M.N>/bundle.json` when the store lacks one, verifies it against
the same digest, and says so.

## Third-party sources

SPEC §6.1 and §6.5 already allow specifications outside the official registry:
their Type URIs sit under another authority, and a slug is unique only within
its authority. Third-party sources let an application pin tasks from another
ecosystem's registry beside official ones, and generate them together.

### The format

The manifest declares each source and names its tasks `<source>:<slug>`:

```toml
# trust-tasks.toml
[sources.acme]                      # name: [a-z][a-z0-9]*(-[a-z0-9]+)*
url = "https://tasks.acme.example"  # https only — or: path = "../acme-registry"

[tasks]
"vault/get" = "0.3"
"acme:payments/settle" = "1.0"
"acme:vault/get" = "0.3"            # acme's own vault/get: another specification
```

The lock stays `version = 1`. It gains `[sources.<name>]` tables (the sources
at least one entry comes from, as the manifest declares them) and an optional
`source` key on each `[[task]]`. Entries are sorted official first, then by
source name, then slug, then version:

```toml
version = 1
registry = "https://trusttasks.org"

[sources.acme]
url = "https://tasks.acme.example"

[[task]]
slug = "vault/get"
version = "0.3"
type_uri = "https://trusttasks.org/spec/vault/get/0.3"
digest = "sha256:…"

[[task]]
source = "acme"
slug = "payments/settle"
version = "1.0"
type_uri = "https://tasks.acme.example/spec/payments/settle/1.0"
digest = "sha256:…"
```

- **Vendored path:** `trust-tasks/@<source>/<slug>/<M.N>.bundle.json`. `@` cannot
  begin a slug, so a source's directory never collides with an official family.
- **Generated namespace:** a source's tasks sit under a top-level module,
  directory or path segment named for the source, cased as a slug segment would
  be — Rust `tasks::acme::payments::settle::v1_0`, Go
  `<out>/acme/payments/settle/v1_0`, TypeScript `<out>/acme/payments/settle/1.0/…`,
  Dart `<out>/acme/payments/settle/v1_0/payload.dart`.
- **Identity comes from the bundle's `typeUri`,** never rebuilt from a slug with
  a hard-coded prefix. A sourced Type URI may be any SPEC §6.1 form:
  `<prefix>/spec/<slug>/<M.N>` for an https authority or a DID URL, or
  `urn:<nid>:<prefix>:spec:<slug-segments>:<M.N>`.
- A source serves the layout trusttasks.org does: `specs/index.json`,
  `specs/<slug>/<M.N>/bundle.json`, `specs/by-digest/sha256-<hex>.json`. A `path`
  source is the same tree on disk, relative to the project.

Generators ignore a source's `url` / `path`; they read only the vendored files.

### The trust model

- **Digests pin content.** As for official tasks, the lock pins each sourced
  bundle by `sha256`, and the build refuses a vendored file that does not match.
  A source can change what it serves; it cannot change what an application
  builds without a reviewed change to the lock. `fetch` restores by digest from
  the source's by-digest store and never moves a pin.
- **The authority rule (SPEC §6.5 item 1).** A sourced bundle whose Type URI is
  under `https://trusttasks.org/` is refused — compared as RFC 3986 compares
  scheme and host, so `HTTPS://TrustTasks.org/…` is caught too — and so is an
  official bundle whose Type URI is not exactly
  `https://trusttasks.org/spec/<slug>/<M.N>`. A source therefore cannot pass its
  specification off as the registry's, and the registry cannot be mirrored into
  serving someone else's.
- **The reservation (SPEC §6.5 item 2).** No source may serve a framework slug
  (`^trust-(task|ceremony)($|-|/)`).
- **One Type URI, one pin.** Two lock entries with the same Type URI — two
  source names for one site, say — are refused.
- **Namespaces cannot collide.** A source named like the first segment of an
  official task in the same lock (`[sources.vault]` beside `vault/get`) is
  refused: the two would share a generated namespace in every language.
- **Consistency.** A bundle whose Type URI, slug and version disagree with each
  other, or with the lock entry it is vendored as, is refused by the CLI and by
  every generator.
- **No network at build.** Generation reads the lock and the vendored bundles
  only. A source's `url` is https-only — over plain http anyone on the path could
  choose the specifications an application generates code for, and SPEC §6.1
  forbids http Type URIs for the same reason. `TRUST_TASKS_CA_FILE` names a PEM
  bundle the CLI trusts instead of the Mozilla roots, for a source behind an
  internal CA.
- **Runtime routing keys by the whole Type URI.** Rust's `Dispatcher` and
  `AsyncDispatcher` key handlers by `TypeUri::for_routing`; the generated
  `EXTENDS` table and `declare_extends()` key by the bundle's full Type URI; and
  the dispatchers' unsupported-*version*-or-*type* decision is keyed by authority
  and slug, so a document of acme's `vault/get` never reaches the registry's
  `vault/get` handler, by exact match, by a forward `extends` route, or as an
  "unsupported version" of it. `examples/consumer-app` dispatches both.

What the rules do not do: a source is trusted to mean what its specifications
say. Pinning `acme:payments/settle` is a decision to trust acme for that
specification, made once and reviewed in the lock; nothing here vets acme's
schemas or prose beyond what building a bundle requires.

### The commands

Consumer side — the existing commands, with `<source>:<slug>` wherever a slug
goes:

```sh
trust-tasks add acme:payments/settle/1.0    # or acme:payments/settle, …@latest
trust-tasks update acme:payments/settle     # says when 1.1 extends 1.0
trust-tasks check                           # offline; also: lock sources = manifest sources
trust-tasks fetch                           # restores trust-tasks/@acme/… by digest
trust-tasks list --remote                   # asks each source for newer versions
trust-tasks remove acme:payments/settle     # drops [sources.acme] when nothing uses it
```

Each command opens a source only when a task it touches comes from it; a
command that touches only sourced tasks never contacts trusttasks.org.
`--registry` / `TRUST_TASKS_REGISTRY` still select only the official registry.

Publisher side — `trust-tasks registry build` turns a third party's
`specs/<slug>/<M.N>/{spec.md,payload.schema.json}` tree into the served layout:

```sh
trust-tasks registry build --specs specs \
  --type-uri-prefix https://tasks.acme.example \
  --out site [--official-specs <checkout>/specs]
```

It writes `site/specs/index.json`, every `bundle.json`, and the by-digest store
(append-only: an existing entry is never rewritten, and one whose bytes are not
its digest stops the build). The builder is `trust_tasks_build::publish` (the
`publish` feature), the one `trust-tasks-codegen --bundles` now builds the
official registry with — moved out of the codegen, which still writes the
official bundles byte for byte as before. A third-party schema may `$ref` the
registry's shared components by absolute URL — the served file
(`https://trusttasks.org/specs/_framework/0.4/framework.schema.json#/$defs/Ext`)
or the component's `$id`. They are read from `--official-specs`, or fetched by
the publisher; the bundle carries them inlined, so no consumer dereferences
anything. `--type-uri-prefix` may be an https site, a DID (`did:web:acme.example`)
or a URN namespace (`urn:acme:tasks`), and never `https://trusttasks.org`.

What the builder checks of a third party's tree: front matter with a known
`status`, and everything needed to compute the bundle's policy (parties,
`proofRequirement`, `issuedAtRequirement`, `maxDocumentBytes`, `bearer`,
`errorCodes`, `extends`); the SPEC §6.1 slug grammar and §5.1 version grammar;
no reserved slug; the authority rule on the prefix; front matter `slug` /
`version` matching the directories; `supersededBy` only on a retired or
withdrawn version; the payload schema's `$id` equal to the Type URI and its
`$schema` 2020-12 (SPEC §6.3); every `$ref` resolvable; and an `extends` naming
an existing version. **Not ported from `scripts/build-registry.mjs`:**
validation against `spec.meta.schema.json` (required prose fields, the category
taxonomy, party shapes), compiling the schema with a JSON Schema validator, the
proof that an `extends` declaration is additive (`schema-compat`), the member
casing, wire-conventions and stale-references lints, validation of examples
against the payload and envelope schemas, `outcomeEvidence`, `methodExtensions`,
`wireCompatibleWith`, `related`, `targetFrameworkVersion` existence, and link
checks. A third-party registry gets the structural guarantees a consumer relies
on, and none of the registry's editorial ones.

### Runtimes

A sourced task's Type URI may be in the URN or DID form, which a runtime that
parses Type URIs must accept. The Rust runtime's `TypeUri` parses every §6.1
form and prints each back exactly; it already refused `http` (its error message
said otherwise; it is corrected). The TypeScript, Go and Dart runtimes are
handled separately.
